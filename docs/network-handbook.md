## 1. 分层：从一根网线到一次点击

网络协议是分层的，每一层只解决一件事，上层不用关心下层怎么实现。

| OSI 七层 | TCP/IP 四层 | 这一层管什么 | 本项目落点 |
|---|---|---|---|
| 应用层 / 表示层 / 会话层 | **应用层** | 数据长什么样、怎么用 | HTTP：`dlcore/httpd.py` 的 `Handler` |
| 传输层 | **传输层** | 端到端可靠传输、端口 | TCP：`ThreadingHTTPServer` |
| 网络层 | **网络层** | 寻址与路由（IP 地址） | IPv4：`0.0.0.0:8848` |
| 数据链路层 / 物理层 | **网络接口层** | 同一网段内怎么把帧送到 | Wi-Fi / 以太网，代码不碰 |

**关键认知**：写应用的人只需要管最上面一层和"端口"这一个传输层概念。下面几层由操作系统代劳——你 `bind(0.0.0.0, 8848)` 之后，内核负责收包、重组、校验、重传。

一次"手机打开电脑页面"的完整路径：

```
手机浏览器 → [HTTP 请求文本] → TCP 分段 → IP 包 → Wi-Fi 帧 → 路由器/热点转发
         → 电脑网卡 → 内核按端口 8848 交给 Python 进程 → Handler 解析 → 回响应
```

## 2. IP 地址与端口

### 2.1 IP 地址 = 网络里的门牌号

IPv4 是 32 位，写成四段十进制，例如 `192.168.1.7`。

**公网地址**：全球唯一，能直接互访。
**私网地址**：只在局域网内有效，不能直接出现在公网上。三段固定区间：

| 区间 | 掩码 | 典型用途 |
|---|---|---|
| `10.0.0.0/8` | 255.0.0.0 | 大企业内网 |
| `172.16.0.0/12` | 255.240.0.0 | 云厂商内网、部分公司 |
| `192.168.0.0/16` | 255.255.0.0 | **家用路由器、手机热点**（最常见） |

本项目 99% 的场景是 `192.168.x.x`——手机热点默认就是 `192.168.43.x` 这种段。

**为什么要懂这个**：`lan_urls()` 里给地址排优先级，`192.168.` 排第一、`10.` 第二、`172.` 第三，就是因为家用场景下 192.168 最可能是"能用的那一个"。

### 2.2 回环地址 127.0.0.1

也叫 localhost。它不经过网卡，内核直接转回来。`127.0.0.1` 永远指"我自己"。

本项目的三个用法：

1. 服务端监听后，电脑自己用 `http://127.0.0.1:8848` 打开界面（见 `server.py` 的启动横幅）。
2. **本机免配对**：`_is_local()` 判断来源 IP 是不是 `127.0.0.1 / ::1`，是就直接放行（`dlcore/httpd.py`）。这是"我自己开的页面不用输配对码"的实现基础。
3. 安卓端 WebView 加载 `http://127.0.0.1:8848`——手机上的服务跑在自己身上。

IPv6 的回环是 `::1`，带端口写 `[::1]:8848`（方括号是必须的，否则冒号分不清）。

### 2.3 0.0.0.0 是什么意思

**它不是"某个地址"，而是"所有地址"**。`bind("0.0.0.0", 8848)` 表示：本机任何一张网卡上、来自任何来源的连接，只要目标是 8848 端口，都交给我。

对比一下：

| 绑定 | 谁能连上 |
|---|---|
| `127.0.0.1:8848` | 只有本机能连，手机连不上 |
| `0.0.0.0:8848` | 本机 + 局域网内所有设备（本项目用这个） |
| `192.168.1.7:8848` | 只有走这张网卡、且目标是这个 IP 的连接 |

本项目两端的监听都是 `0.0.0.0`：Python 侧 `Server(("0.0.0.0", port), Handler)`，安卓侧 `ServerSocket(port, 64, InetAddress.getByName("0.0.0.0"))`。

### 2.4 169.254.x.x 是坏消息

这个段叫 **APIPA**（自动私有 IP 寻址）。设备连上了 Wi-Fi 但没拿到 DHCP 分配的地址时，会自己编一个 `169.254.x.x`。它意味着"链路通了但没人给我发地址"，这种地址基本连不通任何东西。

所以 `lan_urls()` 里有一行 `ips = [ip for ip in ips if not ip.startswith("169.254.")]`——把这种"看起来有地址、其实废的"过滤掉，否则会把一个必然打不开的地址展示给用户。

### 2.5 端口：一台机器上的门牌号

端口是 16 位整数，0–65535。一个 IP + 一个端口，唯一确定一个服务进程。

| 区间 | 用途 |
|---|---|
| 0–1023 | 系统保留（80 HTTP、443 HTTPS、22 SSH），普通程序要管理员权限才能绑 |
| 1024–49151 | 注册端口，普通程序随便用 |
| 49152–65535 | 临时端口，操作系统分配给"发起连接的一方" |

本项目选 **8848**：落在自由区间，好记，且不撞常见服务。

**端口冲突是真实存在的**：如果 8848 已被别的程序占用，`bind()` 会抛 `OSError`。代码的处理是**往后找 20 个端口**：

```python
for offset in range(0, 20):
    try:
        httpd = Server(("0.0.0.0", port + offset), Handler)
        port = port + offset
        break
    except OSError:
        continue
```

所以启动横幅里显示的端口才是实际端口——**永远以横幅/`/api/ping` 为准，不要假设一定是 8848**。这也是测试脚本容易踩的坑。

## 3. TCP

### 3.1 三次握手、四次挥手

HTTP 跑在 TCP 上。建立连接要三次握手：

```
客户端 ── SYN ──────────→ 服务端      "我想连你，我的序号是 x"
客户端 ←─ SYN+ACK ─────── 服务端      "收到，我的序号是 y，确认 x"
客户端 ── ACK ──────────→ 服务端      "确认 y"
```

三次的目的：**双方都确认"我能发、你能收"和"你能发、我能收"**。两次不够——服务端无法确认客户端收到了自己的 SYN。

关闭是四次挥手（FIN / ACK / FIN / ACK），因为 TCP 是全双工，两个方向要各自关。

### 3.2 为什么取消下载会看到 RST

用户点"取消"时，客户端直接关掉 socket，但还有数据在路上。内核收到对端发来的数据、发现连接已经没了，就回一个 **RST**（Reset）。

Python 侧表现为 `ConnectionResetError`（Windows 上常见 `WinError 10054`，即"远程主机强迫关闭了一个现有连接"），写入方向则是 `BrokenPipeError`。

**这是正常事件，不是错误**。但 Python 标准库默认把它当未捕获异常，打一整段 Traceback。1.4.0 专门修了这点：

```python
def handle_error(self, request, client_address):
    if isinstance(exc, (ConnectionResetError, ConnectionAbortedError, BrokenPipeError)):
        print(f"[断连] {ip}:{port} {type(exc).__name__}")   # 只记一行
        return
```

修之前，一次取消下载能往日志里写几十行堆栈，真异常会被淹没——这也是复测时探针误报 CRIT 的原因。

### 3.3 keep-alive：别为每个请求重新握手

HTTP/1.0 默认一个请求一个连接，用完就关。HTTP/1.1 默认**长连接**：一个 TCP 连接上可以连续发多个请求。

本项目显式声明 `protocol_version = "HTTP/1.1"`，所以：

- 页面加载 `index.html + app.js + styles.css` 复用同一条 TCP，省掉两次握手；
- 好处是快，代价是**连接会一直挂着**，所以服务端要有并发上限（下一节）。

什么时候主动关：请求体读不完、鉴权失败需要断开、以及 `close_connection = True` 的显式标记（例如 411/413 之后不读剩余的 body，直接断，避免把脏数据当成长连接的下一帧）。

### 3.4 并发模型：本例最多能扛多少

三层限制，从外到内：

| 层 | 机制 | 数值 | 超了会怎样 |
|---|---|---|---|
| 内核 accept 队列 | `request_queue_size` | 64 | 新连接被拒绝/超时 |
| 应用并发槽 | `BoundedSemaphore(64)` | 64 | 第 65 个请求等 10 秒，仍未拿到槽就回 `503` + `Retry-After: 5` |
| 线程模型 | 每个连接一个线程（`ThreadingHTTPServer`） | 同上 | 线程数随并发线性增长 |

**为什么用线程而不是异步**：这是局域网小工具，并发量级是"一两台设备"，线程模型写起来直观、调试友好。真上到几百并发才需要考虑 asyncio。

## 4. HTTP 报文

### 4.1 报文长什么样

HTTP 是**纯文本协议**（正文可以是二进制）。一个请求：

```http
GET /api/list?path=C%3A%2FUsers HTTP/1.1
Host: 192.168.1.7:8848
Cookie: dlsess=abc123
Accept-Encoding: gzip
Range: bytes=0-
```

结构固定为四段：

```
请求行      ← 方法 + 路径 + 版本
头部若干行   ← 键: 值
空行        ← 必须有，标志头部结束
正文        ← GET 一般没有，POST 有
```

响应同理：

```http
HTTP/1.1 206 Partial Content
Content-Type: application/octet-stream
Content-Length: 1048576
Accept-Ranges: bytes
Content-Range: bytes 0-1048575/5242880

<二进制数据>
```

**一条铁律**：头部里的字节数一律是**字节**，不是字符。中文一个字符在 UTF-8 下是 3 字节，`Content-Length` 必须算 3。

### 4.2 本项目用的方法

| 方法 | 用在哪 | 说明 |
|---|---|---|
| `GET` | 列目录、预览、下载、查状态 | 只读，可缓存，可带 Range |
| `POST` | 登录、上传、删除、改名、建文件夹 | 有副作用 |
| `HEAD` | 探测文件大小/是否支持 Range | 和 GET 一样，但不回正文（`do_HEAD = do_GET`，靠 `self.command` 判断是否写 body） |

**注意：删除也用 POST**（`POST /api/delete`），不是 `DELETE`。原因是避免某些代理/安全软件拦截非标准方法，也避开 WebView 对 `DELETE` 的预检。这是工程妥协，不是协议要求。

### 4.3 状态码：本项目实际用到的 17 个

| 码 | 含义 | 本项目的触发条件 |
|---|---|---|
| `200` | 成功 | 绝大多数正常响应 |
| `204` | 成功但无正文 | 图标生成失败时的兜底 |
| `206` | 部分内容 | Range 请求命中，返回一段字节 |
| `304` | 未修改 | 静态资源 ETag 命中，省掉重传 |
| `400` | 请求有误 | JSON 解析失败、PIN 格式不对、路径为空 |
| `401` | 未认证 | 没配对 / 会话过期 |
| `403` | 拒绝 | Origin 不合法、访问系统保护目录、降级时路径校验不可用 |
| `404` | 不存在 | 文件/文件夹不在、分享链接过期 |
| `409` | 冲突 | 目标已有同名文件 |
| `411` | 需要长度 | 上传没带 `Content-Length`（无法知道读多少） |
| `413` | 太大 | 上传超 64 GB、打包内容过大 |
| `414` | URI 过长 | 二维码内容超 512 字节（语义近似，见下） |
| `416` | 范围不满足 | Range 越界或倒序（`bytes=5-1`），响应带 `Content-Range: bytes */size` |
| `421` | 请求被误导 | `Host` 头不是本机地址（防 DNS 重绑定） |
| `429` | 太频繁 | 配对码连续错 5 次后指数退避锁定 |
| `500` | 服务端错误 | 未预期异常，只回一个错误号，详情写日志 |
| `503` | 暂不可用 | 并发槽满（带 `Retry-After`）、模块降级时的接口 |
| `507` | 存储不足 | 上传时磁盘剩余空间不够 |

> 414 的小瑕疵：二维码内容过长严格说更接近 413。这里沿用 414 是历史选择，不影响功能，属于"可以不改但值得知道"的一类。

**状态码的选择原则**：让客户端能**不读正文就做出判断**。401 要重登、403 要换路径、416 要改 Range、429 要等——全靠码本身。

## 5. 本项目用到的 HTTP 机制

### 5.1 Content-Length：怎么知道读到哪里算一个请求结束

HTTP/1.1 有两种定界方式：

1. **`Content-Length`**：先告诉我多少个字节，读完这么多就是一个完整请求。
2. **`Transfer-Encoding: chunked`**：边发边告诉长度，每块前面写块大小，最后一块是 0。

本项目**只用第一种**。理由很实在：

- 上传时浏览器知道文件大小，直接给 `Content-Length` 最简单；
- 服务端读循环就是"读到 `length` 为止"，不需要状态机；
- **拿不到长度时必须明确拒绝**，否则会一直读下去，把连接里后面的内容当成正文——这就是 `411 Missing Content-Length` 的存在意义。

读取的实现（`dlcore/api.py`）：

```python
while received < length:
    chunk = self.rfile.read(min(CHUNK, length - received))   # CHUNK = 512 KB
    if not chunk:
        break
    f.write(chunk)
    received += len(chunk)
```

`if not chunk: break` 处理的是"对端提前断开"——这时 `received < length`，文件是残缺的，必须删掉临时文件而不是当成功。

### 5.2 为什么上传用原始 body，不用 multipart/form-data

表单上传（`<input type=file>`）通常用 `multipart/form-data`：把文件切成带边界字符串的段，一段一个字段。

本项目**不用**，而是 `POST /api/upload?name=xxx&rel=yyy` + 原始二进制 body。原因：

| 考虑 | multipart | 原始 body |
|---|---|---|
| 解析复杂度 | 要解析边界、处理转义 | 直接读字节 |
| 内存 | 容易把整个文件读进内存 | 可以流式边读边写 |
| 断点续传 | 偏移量难算（有边界开销） | 偏移量就是字节偏移 |
| 进度 | 需要额外解析 | `已收字节 / 总字节` 直接算 |

代价是**一次只能传一个文件**，元数据只能塞在 query 里（`name`、`rel`）。对"传文件"这个单一场景，这笔交易划算。

### 5.3 Range：断点续传的全部秘密

`Range` 是 HTTP/1.1 的可选特性：客户端说"我只要第 1000 到 1999 字节"，服务端回 `206` + 那一小段。

三种写法：

| 请求 | 含义 |
|---|---|
| `Range: bytes=0-499` | 前 500 字节 |
| `Range: bytes=500-` | 从 500 到结尾 |
| `Range: bytes=-500` | **最后** 500 字节（注意：是后缀，不是"从 0 到 500"） |

服务端要回：

```http
HTTP/1.1 206 Partial Content
Accept-Ranges: bytes
Content-Range: bytes 0-499/5242880     ← 这一段 / 总大小
Content-Length: 500
```

**关键点**：`Content-Range` 里的总大小是断点续传能成立的前提——客户端靠它知道"还差多少"。

不合法的 Range 要回 `416`，且带 `Content-Range: bytes */总大小`，告诉客户端正确的大小是多少。本项目连"倒序区间"（`bytes=5-1`）也判 416，符合 RFC 9110。

**断点续传的完整逻辑**（客户端侧，`DownloadCenter.kt`）：

1. 下载时先写 `<任务id>-<文件名>.part`，不直接写目标文件；
2. 中断后保留 `.part`，记录已下载字节数；
3. 重试时发 `Range: bytes=<已下载>-`；
4. 服务端回 206，客户端**追加**写入；
5. 下完校验 SHA-256，通过才 `rename` 成正式文件名。

**为什么必须有第 5 步**：Range 续传只保证"字节位置对"，不保证"内容对"。中间换过一次文件（同名覆盖），拼起来就是错的，且长度可能刚好对得上。哈希是唯一能发现这种情况的手段。

### 5.4 ETag 与 304：别重复传一样的东西

`ETag` 是资源的版本指纹。本项目用「修改时间纳秒 + 文件大小」拼：

```python
etag = '"%x-%x"' % (st.st_mtime_ns, st.st_size)
```

客户端第二次请求带 `If-None-Match: "指纹"`，服务端比对一致就回 `304 Not Modified`，**不带正文**。浏览器直接用本地缓存。

省的是什么？`app.js` 有 2300 多行、`styles.css` 一千多行，每次刷新都重传约 100 KB；304 之后只有几百字节的响应头。

**为什么不用 Last-Modified**：它的精度是秒。同一秒内改两次文件，指纹不变，客户端会拿到旧内容。`mtime_ns` 没这个问题。

**注意 `Cache-Control`**：本项目静态资源用 `no-cache`（**不是** `no-store`）。`no-cache` 的意思是"可以缓存，但每次用之前要问一下我有没有变"——配合 ETag 就是最优解：没变就 304，变了才重传。`no-store` 则是"完全不许缓存"，会每次都全量重传。

### 5.5 gzip：文本能压掉七成

请求带 `Accept-Encoding: gzip` 时，服务端可以把文本资源压缩后再发，响应头加：

```http
Content-Encoding: gzip
Vary: Accept-Encoding
```

`Vary` 的作用是告诉缓存层："同一个 URL，不同的 `Accept-Encoding` 要分开缓存"。漏了它，中间代理可能把 gzip 版本发给不支持 gzip 的客户端，直接乱码。

**哪些能压**：`text/*`、`application/javascript`、`application/json`、`image/svg+xml`。
**哪些不能压**：`image/png`、`image/jpeg`、`video/*`、`application/zip`——这些本来就压缩过，再压一遍只会变大、还费 CPU。

本项目在发送前判断 MIME 类型，只压可压缩的；并且**按文件指纹缓存压缩结果**（`_STATIC_CACHE`），避免每次请求都重新压一遍。

### 5.6 Content-Type 与 MIME

`Content-Type` 告诉客户端"这段字节是什么"。格式：`类型/子类型; charset=编码`。

常见的：

| 类型 | 用途 |
|---|---|
| `text/html; charset=utf-8` | 页面 |
| `application/json; charset=utf-8` | 接口返回 |
| `text/plain; charset=utf-8` | 纯文本、错误消息 |
| `application/octet-stream` | 未知二进制（让浏览器走下载） |
| `image/png` | 图标、二维码 |
| `application/manifest+json` | PWA 清单 |

**`application/octet-stream` 是个开关**：用它可以强制浏览器下载而不是内联打开。本项目下载接口靠 `Content-Disposition` 配合，另外 `inline=1` 参数可以让 PDF/图片直接预览。

**中文文件名**要用 RFC 5987 的 `filename*=UTF-8''%E4%B8%AD%E6%96%87.zip` 形式，否则在部分浏览器上会变成乱码或被截断。

### 5.7 URL 编码：为什么中文路径要变成 %E4%B8%AD

URL 里只允许一小撮 ASCII 字符（字母、数字、`-_.~`），其余必须转义成 `%XX`（XX 是该字节的十六进制）。

- 空格 → `%20`
- 中文「中」→ UTF-8 是 `E4 B8 AD` → `%E4%B8%AD`
- `&`、`=`、`?`、`#` 在 URL 里有特殊含义，出现在参数值里必须转义，否则会被当成参数分隔符

**本项目的坑点**：路径参数里全是 `\`、`:` 和中文。`C:\Users\张三\文件.txt` 必须整体编码后放进 `?path=`，否则：

- `\` 在某些客户端会被规范化成 `/`；
- `#` 后面的内容会被当成锚点丢掉；
- `&` 会把一个参数切成两个。

服务端拿到后要 `urllib.parse.unquote` **还原一次**，且还原要在路径校验**之前**——否则 `%2e%2e%2f` 就能绕过目录检查（路径穿越）。

### 5.8 Cookie 与 Session

HTTP 是**无状态**的：服务端天生不记得"上一个请求是谁发的"。要记，就得靠 Cookie。

流程：

1. 客户端配对成功 → 服务端 `Set-Cookie: dlsess=<随机令牌>`
2. 之后每个请求，浏览器自动带上 `Cookie: dlsess=<令牌>`
3. 服务端查这个令牌对应哪个会话

本项目的 Cookie 属性：

```http
Set-Cookie: dlsess=<token>; Path=/; Max-Age=2592000; HttpOnly; SameSite=Strict
```

逐个解释：

| 属性 | 作用 | 不加会怎样 |
|---|---|---|
| `Path=/` | 整个站点都带上 | 只在某个子路径生效，其他接口 401 |
| `Max-Age=2592000` | 30 天后过期（秒） | 关掉浏览器就没了（会话 Cookie） |
| `HttpOnly` | JS 读不到 `document.cookie` | XSS 一旦注入就能偷走令牌 |
| `SameSite=Strict` | 跨站请求不带这个 Cookie | 别的网站能借你的登录态发请求（CSRF） |

**令牌不是密码**：它是 `secrets.token_urlsafe()` 生成的随机串，服务端在内存里维护 `token → {ip, 创建时间, 最后活动}` 的映射。两套过期：

- **空闲过期**：7 天没动就失效（`SESSION_IDLE_TTL`）
- **绝对过期**：无论多活跃，30 天必须重登（`SESSION_ABS_TTL`）

**为什么要绝对过期**：令牌一旦泄露（截图、日志、共享电脑），没有绝对过期就是永久后门。

### 5.9 为什么本机令牌放在 URL 里（?k=）

程序自己拉起浏览器时用 `http://127.0.0.1:8848/?k=<token>`。

为什么不放请求头？因为**浏览器地址栏打开的页面，没法给它加自定义头**。要么放 URL，要么放 Cookie——而首次打开时还没有 Cookie。所以只能放 URL。

代价：URL 会进浏览器历史、可能进 Referer。缓解手段是同时设 `Referrer-Policy: no-referrer`，并让这个令牌**只对 127.0.0.1 来源生效**（外部 IP 拿到也没用，仍然要配对码）。

### 5.10 安全响应头：为什么每个响应都带

`_send()` 里固定加三个头：

| 头 | 作用 |
|---|---|
| `X-Content-Type-Options: nosniff` | 禁止浏览器"猜"类型。否则一个伪装成 .txt 的 HTML 会被当页面执行 |
| `Referrer-Policy: no-referrer` | 跳转时不带来源 URL，避免路径/令牌泄漏给第三方 |
| `X-Frame-Options: DENY` | 禁止被别的网站用 iframe 嵌套（防点击劫持） |
| `Content-Security-Policy` | 限制只能加载同源资源、禁内联脚本（加固模式） |

这些不是"形式主义"：没有 `nosniff`，上传一个 `.txt` 里写 `<script>` 就可能变成存储型 XSS 的入口。

## 6. 局域网与 Wi-Fi

### 6.1 私网、掩码、网关、DHCP

家用网络的典型结构：

```
手机/电脑 192.168.1.7  ──┐
电视      192.168.1.9  ──┼── 路由器 192.168.1.1（网关）── 光猫 ── 互联网
电脑      192.168.1.20 ──┘
```

- **子网掩码** `255.255.255.0`（即 `/24`）：前三段相同就是"同一个网段"，可以直接通信，不用经过网关。
- **网关**：不在同网段时的出口，通常是 `.1`。
- **DHCP**：自动发地址的服务。设备连上 Wi-Fi 后先问"我该用哪个地址"，路由器从池子里分一个，并给个租期。

**对本项目的意义**：两台设备必须在**同一个网段**（前三段相同，或至少在同一个子网内）才能直连。手机连的是 `192.168.1.x`、电脑连的是 `192.168.2.x`，就算在同一个物理房间也互相看不见——这是"输对 IP 还是打不开"的头号原因。

### 6.2 手机热点 = 手机变成了路由器

开热点时，手机扮演三个角色：**DHCP 服务器 + NAT 网关 + 无线 AP**。

- 手机自己通常是 `192.168.43.1`（不同厂商可能不同）；
- 连进来的电脑会被分配 `192.168.43.x`；
- 电脑访问 `192.168.43.1:8848`，就是访问手机上的服务。

本项目的 `HotspotManager.apIp()` 就是枚举网卡名里带 `ap` / `wlan` / `softap` 的接口，取 `192.168.` 或 `10.` 开头的地址——因为**热点网卡的名字各厂商不一样，但网段是固定的几种**。

**NAT 的影响**：手机热点下，外部（比如手机自己的移动网络）访问不到电脑；只有热点内部的设备能互访。这对本项目正好够用。

### 6.3 AP 隔离：连上了却打不开的最常见原因

很多公共 Wi-Fi（酒店、公司、商场）开了**客户端隔离**（AP Isolation / Client Isolation）：允许每台设备上网，但**禁止设备之间互相通信**。

症状非常典型：

- 手机显示已连 Wi-Fi，能刷网页；
- 电脑上服务也正常启动了；
- 但手机打不开 `http://192.168.x.x:8848`，一直转圈或"无法访问"。

**这不是代码问题，代码改不了**。要么换网络（用手机热点最快）、要么关掉路由器的隔离选项（家里路由器一般默认关闭，公共网络通常开）。

识别方法：让手机 ping 电脑的 IP，如果 ping 不通但两台都能上网，基本就是隔离。

### 6.4 2.4 GHz / 5 GHz / Wi-Fi 6：为什么实测只有十几 MB/s

先做单位换算，这是最容易搞混的地方：

```
1 字节(B) = 8 比特(b)
100 Mbps（兆比特每秒）= 100 / 8 = 12.5 MB/s（兆字节每秒）
```

`Mbps` 是带宽单位，`MB/s` 是文件复制速度。差了 8 倍。

然后是"标称速率"和"实际吞吐"的差距：

| 场景 | 标称 | 实际单流吞吐 | 说明 |
|---|---|---|---|
| 2.4 GHz 802.11n | 150 Mbps | 8–15 MB/s | 干扰多，只有 3 个不重叠信道 |
| 5 GHz 802.11ac | 867 Mbps | 30–60 MB/s | 干扰少，穿墙差 |
| Wi-Fi 6 (5 GHz) | 1200 Mbps+ | 60–100 MB/s | 需要路由器和终端都支持 |
| 手机热点 | — | 5–25 MB/s | 手机 CPU 做 NAT，是瓶颈 |
| 千兆有线 | 1000 Mbps | 100–115 MB/s | 受磁盘速度限制 |

**为什么实际只有一半甚至更少**：

1. **半双工**：Wi-Fi 同一时刻只能一方说话，收和发要排队；
2. **协议开销**：每个数据帧都有头、确认、退避；
3. **干扰**：2.4 GHz 上微波炉、蓝牙、邻居路由器都在抢；
4. **单流 vs 多流**：手机往往是 1×1 或 2×2 天线；
5. **对端不是我**：如果同时有别的设备在下载，带宽被分掉。

所以"宿舍千兆宽带，传文件只有 12 MB/s"通常是正常的——瓶颈在 Wi-Fi 那一跳，不在代码，也不在宽带。

### 6.5 为什么本项目不做"自动发现"

很多同类工具会用 UDP 广播或 mDNS 自动找对方（"打开就能看到附近设备"）。本项目**故意不做**，改用二维码：

| 方案 | 优点 | 缺点 |
|---|---|---|
| UDP 广播 | 无需输入 | 被 AP 隔离/防火墙拦、多网卡选错、企业网禁广播 |
| mDNS/Bonjour | 标准、跨平台 | Windows 默认没装、Android 支持参差、`.local` 解析经常失败 |
| **二维码带 IP** | 100% 可靠、零依赖、可截图分享 | 需要对方扫一下 |

本质是取舍：**宁可少一步自动化，也不要多一个"为什么搜不到"的故障点**。

顺带说明：安卓清单里声明了 `CHANGE_WIFI_MULTICAST_STATE`（组播锁），但**代码里并未使用**——那是早年想做自动发现留下的，属于可以清理的死权限。

## 7. 名字解析

### 7.1 域名是怎么变成 IP 的

输入 `www.example.com` 后，系统依次查：

1. **本机 hosts 文件**（`C:\Windows\System32\drivers\etc\hosts`）
2. **本地 DNS 缓存**
3. **DNS 服务器**（运营商或 8.8.8.8 之类），递归查询
4. 拿到 IP 再发起 TCP 连接

### 7.2 为什么本项目全程用 IP，不用域名

局域网设备**没有域名**。想让手机访问 `droplink.local`，需要 mDNS 或自建 DNS，两个都不可靠（见 6.5）。

所以：

- 服务端把 `http://192.168.1.7:8848` 直接算出来、显示出来、编成二维码；
- 客户端连的就是这个 IP:端口；
- 唯一用 `localhost` 的地方是**本机自己访问自己**，那个名字由系统 hosts 保证解析。

### 7.3 一个常被忽略的坑：Host 头

即使你用 IP 访问，请求里也会带 `Host: 192.168.1.7:8848`。服务端可以校验它。

**为什么重要**：攻击者可以把自己的域名解析到你的局域网 IP（DNS 重绑定），诱导你浏览器访问 `http://evil.com:8848`，此时请求打到你电脑上的服务，但 `Host` 是 `evil.com`。如果服务端不校验 Host，就分不清这是"正常访问"还是"被劫持的跨站请求"。

本项目的做法：`_host_ok()` 校验 Host 必须是本机 IP/localhost，否则回 **`421 Misdirected Request`**（加固模式下生效）。

## 8. 地址是怎么找出来的

`lan_urls()` 干的事：**在没有用户输入的前提下，猜出"别人该用哪个地址访问我"**。

### 8.1 技巧一：UDP connect 不发包

```python
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.connect(("8.8.8.8", 80))
ip = s.getsockname()[0]
```

UDP 是无连接的，`connect()` **不会真的发包**，只是让内核查一次路由表："如果我要去 8.8.8.8，该走哪张网卡？"然后把这个网卡的地址告诉你。

这比"枚举所有网卡再猜"准确得多，尤其是有 VPN、虚拟机网卡、Docker 网卡的时候。

### 8.2 技巧二：兜底枚举

UDP 失败（比如完全没网）时，退回 `socket.getaddrinfo(socket.gethostname(), ...)` 枚举本机 IPv4。

### 8.3 为什么还要排序和过滤

一台电脑可能同时有：Wi-Fi `192.168.1.7`、有线 `10.0.0.5`、VMware `192.168.56.1`、Docker `172.17.0.1`、蓝牙 `169.254.x.x`。

**给用户看哪个？** 本项目的规则：

1. 过滤 `169.254.`（APIPA，必然不通）；
2. `192.168.` 优先（家用最常见）；
3. 其次 `10.`；
4. 再次 `172.`；
5. 其他最后。

排序错了的后果很具体：用户照着横幅输地址，输的是 VMware 网卡的 `192.168.56.1`，永远连不上。

## 9. 安全边界：明文 HTTP 到底意味着什么

### 9.1 明文 = 同一个 Wi-Fi 上的人可能看得到

本项目用 **HTTP 而不是 HTTPS**，所有内容（包括配对码、文件名、文件内容）在链路上是**明文**。

这意味着：

- 同一个 Wi-Fi 下的攻击者，用抓包工具能看到你传了什么；
- 在公共 Wi-Fi（咖啡厅、酒店）上，这个风险是真实的；
- 在家里/自己手机热点上，风险基本等于"同住的人"。

**为什么不上 HTTPS**：

| 方案 | 问题 |
|---|---|
| 自签证书 | 每次连接都弹"证书不受信任"，比明文更吓人 |
| 公信 CA 证书 | 需要域名，而局域网只有 IP；给 IP 签证书不现实 |
| 自建 CA + 手动装证书 | 手机端操作复杂，绝大多数用户会放弃 |
| Let's Encrypt | 同上，签不了内网 IP |

这是**有意识的取舍**：产品定位是"同一个 Wi-Fi 下、点对点、不经过服务器"，而不是"跨公网安全传输"。文档里必须写清楚边界，而不是假装安全。

**降低风险的具体做法**（都已实现）：

- 配对码是必须的（陌生人连上也不知道码）；
- 会话有绝对过期（30 天）；
- 连续错 5 次指数退避锁定（60s → 120s → 240s，上限 5 分钟）；
- 敏感目录（`C:\Windows`、用户配置等）在加固模式下拒绝访问；
- 关闭时不留后台监听。

### 9.2 Origin 校验与 CSRF

`Origin` 头告诉服务端"这个请求是哪个页面发起的"。

场景：你浏览器开着 `evil.com`，它偷偷向 `http://192.168.1.7:8848/api/delete` 发一个 POST。浏览器会带上你的 Cookie（如果 `SameSite` 没设或设成 `None`），请求就以你的身份执行了——这就是 **CSRF**（跨站请求伪造）。

本项目两道防线：

1. Cookie 带 `SameSite=Strict`（跨站请求根本不带 Cookie）；
2. 服务端校验 `Origin`，不是自己人回 `403`。

### 9.3 路径穿越：`../` 是怎么逃出目录的

如果服务端把用户传来的路径直接拼：

```python
path = os.path.join(BASE, user_input)     # user_input = "../../Windows/System32/config"
```

就会跑到 `BASE` 外面去。变体还有 URL 编码过的 `%2e%2e%2f`、双重编码、以及 Windows 特有的 `..\` 和 `\\?\` 前缀。

本项目的防线：

- 先 `unquote` **再**校验（顺序错了等于没校验）；
- `os.path.abspath` 规范化后，用 `os.path.commonpath` / 前缀比对确认仍在允许范围内；
- 拒绝 UNC 路径（`\\server\share`）、ADS（`file.txt:stream`）、含 NUL 的路径；
- 加固模式下额外拒绝系统目录。

**核心原则**：**先规范化，再判断，最后才用**。判断和使用之间不能再有任何字符串变换。

### 9.4 会话固定与令牌强度

如果登录前后令牌不变，攻击者可以先给你种一个他知道的令牌，等你登录后他就有了你的会话——这叫**会话固定**。

本项目的做法：登录成功时**重新生成**令牌（`STATE.new_session()`），不复用任何已有值；令牌来自 `secrets`（密码学安全随机），不是 `random`。

**`random` 和 `secrets` 的区别**：前者是可预测的伪随机（种子可推），后者用操作系统的熵源。用来生成令牌/密码必须用后者。

## 10. 中间设备：为什么"我这儿好好的，你那儿打不开"

### 10.1 Windows 防火墙的三种配置文件

Windows 防火墙按**网络类型**套用不同规则：

| 配置文件 | 什么时候用 | 默认行为 |
|---|---|---|
| 专用（Private） | 你信任的网络（家里） | 允许部分入站 |
| 公用（Public） | 咖啡厅、机场 | **几乎全拦** |
| 域（Domain） | 公司域环境 | 由管理员策略决定 |

**最常见的坑**：家里 Wi-Fi 被 Windows 识别成"公用网络"，于是 8848 端口的入站被拦，手机连不上，但电脑自己 `127.0.0.1` 一切正常。

本项目的 `/api/firewall/set` 就是干这个的：调用 `netsh advfirewall` 给当前配置文件加一条放行规则。加固模式下还会检查"规则覆盖的网络类型是否和当前网络匹配"——因为只放行了"专用"、而当前是"公用"，等于没放。

### 10.2 代理：为什么 `curl 127.0.0.1` 也会失败

如果系统设了 `HTTP_PROXY`，很多工具会**连本地地址也走代理**。代理服务器当然访问不到你本机的 8848，于是超时。

所以测试脚本里经常看到：

```bash
curl --noproxy '*' http://127.0.0.1:8848/api/ping
```

`--noproxy '*'` = 本次请求不走任何代理。

**这不是代码 bug**，是环境问题。真要排查，先看 `echo $HTTP_PROXY`。

### 10.3 VPN 与虚拟网卡

开 VPN 后，路由表被改，默认出口变成 VPN 网卡。后果：

- `lan_urls()` 的 UDP 探测可能拿到 VPN 的地址（如 `10.8.0.6`）；
- 手机在同一 Wi-Fi 下，访问 `10.8.0.6` 根本到不了。

这就是为什么要"枚举 + 排序"而不是只取一个地址。同理，VMware/VirtualBox/Docker 的虚拟网卡也会贡献一堆"看起来像内网"的地址。

### 10.4 杀毒软件的流量扫描

部分安全软件会劫持本地回环流量（做 HTTPS 中间人）。表现是：`127.0.0.1` 的请求偶发失败或延迟异常。排查时可以先临时关闭"网页防护"验证。

## 11. 性能

### 11.1 先学会换算

```
带宽(bps) ÷ 8 = 吞吐(B/s)
```

| 标称 | 理论峰值 | 现实预期 |
|---|---|---|
| 100 Mbps | 12.5 MB/s | 10–11 MB/s |
| 1 Gbps | 125 MB/s | 100–115 MB/s（受磁盘限制） |
| Wi-Fi 5 (867 Mbps) | 108 MB/s | 30–60 MB/s |

**用户说"传得好慢"，先问：多少 MB/s？什么网络？** 12 MB/s 在百兆网络上就是满速，不是 bug。

### 11.2 延迟与滑动窗口（为什么跨公网快不了）

TCP 不是"发一个等一个确认"，而是"在窗口允许的范围内连续发"。窗口能容纳的数据量受 **带宽 × 往返延迟（BDP）** 限制：

```
100 Mbps × 10 ms RTT = 1 Mbit ≈ 125 KB
```

也就是说，链路上同时最多只能有 125 KB 在飞。如果窗口小于这个值，带宽就用不满。

**局域网 RTT 通常 < 2 ms**，所以这个限制在本项目里基本不存在——这也是为什么"局域网直连"能跑满带宽，而"云中转"永远慢一截（要绕一圈公网）。

### 11.3 为什么分块是 512 KB

代码里 `CHUNK = 512 * 1024`，读文件和发文件都按这个粒度。

| 分块太小 | 分块太大 |
|---|---|
| 系统调用次数多，CPU 花在切换上 | 单次占用内存大，64 并发时容易爆 |
| 进度更新太频繁 | 进度条跳变大 |

512 KB 是个折中：64 并发 × 512 KB ≈ 32 MB 峰值内存，同时单次读写的系统调用开销可忽略。

### 11.4 队列与并发

安卓端下载队列**串行执行、上限 5 个**。为什么串行：

- 手机 Wi-Fi 是半双工，同时下 5 个文件总吞吐不会更高，反而每个都慢；
- 串行让"暂停/继续"的语义简单（不用处理多个流的抢占）；
- 用户能清楚知道"现在在下哪个"。

### 11.5 SHA-256 的代价

对文件做哈希是**全量读一遍**，CPU 密集。本机（i7-14650HX，带 SHA 指令集）实测：

```
256 MB / 0.21 s ≈ 1210 MB/s
```

按这个速度：

- 100 MB 文件 ≈ 0.08 秒；
- 512 MB 文件 ≈ 0.4 秒。

旧机器或没有 SHA 扩展的 CPU 会慢很多（300–500 MB/s），所以代码里没有假设"哈希一定很快"——它放在下载完成之后执行，不阻塞传输，且只对 **≤ 512 MB** 的文件做。

为什么不给所有文件都做：GB 级文件在慢机器上要几秒，用户会觉得"下完了怎么还卡着"；而校验的价值集中在"大文件传输出错概率更高"这一段，取舍点在 512 MB。

## 12. 排障手册

按症状查。命令以 Windows 为主。

| 症状 | 先查什么 | 命令 | 常见原因 |
|---|---|---|---|
| 手机打不开页面 | 两台在不在同一网段 | `ipconfig`（电脑）/ 手机看 Wi-Fi 详情 | 一个连 2.4G 一个连 5G 但不同子网、连了不同网络 |
| 同上 | 端口通不通 | `ping 192.168.1.7` 然后 `curl -v http://192.168.1.7:8848/api/ping` | 防火墙拦截、AP 隔离 |
| 同上 | 服务真起来了吗 | 浏览器开 `http://127.0.0.1:8848` | 服务没启动、端口被占（看横幅实际端口） |
| 电脑自己能开、手机不行 | 防火墙 | `netsh advfirewall show currentprofile` | 网络被识别为"公用" |
| 偶尔能连、偶尔不能 | 地址是不是变了 | 对比横幅 IP 与手机输入的 IP | DHCP 重新分配、多网卡选错 |
| 传文件中断 | 是不是大文件 | 看文件大小与日志 | Wi-Fi 信号弱、手机省电杀后台 |
| 下载完文件损坏 | 校验过没过 | 对比两端 SHA-256 | 续传拼接错、磁盘满 |
| 上传 90% 失败 | 有没有断点续传 | — | **当前版本上传不支持续传**，只能重来 |
| 302/无法访问但 ping 通 | 代理 | `echo $HTTP_PROXY` | 代理劫持了请求 |
| 打开是空白页 | 静态资源 404 | `curl -o /dev/null -w "%{http_code}" http://IP:8848/static/app.js` | 安装不完整（少了 web 目录） |
| 配对码一直错 | 是不是锁定了 | 换一台设备试 | 连错 5 次触发 429 退避 |
| 扫码页黑屏 | 相机权限 | 系统设置看权限 | 权限被拒、其他应用占用相机 |

**一个万能顺序**：先在自己机器上 `127.0.0.1` 验证服务，再在同网段另一台设备验证网络，最后才怀疑代码。这三步能把 90% 的问题定位到具体一层。

## 14. 本项目**没有**用到的（以及为什么）

写清楚"不用什么"，比只写"用什么"更能说明设计边界。

| 技术 | 为什么不用 |
|---|---|
| **HTTPS / TLS** | 局域网只有 IP、没有域名，证书方案全部不可行或体验极差；见 9.1 |
| **WebSocket** | 进度查询 1.5 秒轮询一次就够，WS 要处理握手、心跳、重连，收益不成比例 |
| **SSE（Server-Sent Events）** | 同上，且需要长连接占用并发槽 |
| **HTTP/2、HTTP/3(QUIC)** | 单连接、少量请求，多路复用带来的收益为零；HTTP/3 还要 UDP 打洞，更复杂 |
| **multipart/form-data** | 单文件上传用原始 body 更简单、可断点；见 5.2 |
| **chunked 传输** | 上传时长度已知，直接给 Content-Length，读循环最简单；见 5.1 |
| **UDP 广播 / mDNS 自动发现** | 被 AP 隔离、防火墙、多网卡反复坑，改用二维码；见 6.5 |
| **FTP / SMB** | 需要额外服务、账号体系，且手机端支持差 |
| **IPv6 优先** | 局域网里 IPv6 地址不稳定（临时地址会变），用 IPv4 更可靠 |
| **CDN / 反向代理** | 没有公网入口，也没有跨地域访问需求 |
| **断点续传（上传方向）** | 服务端已具备 `.part` 与原子改名的基础，但协议还没做——这是下一版的主要缺口 |
