# DropLink 分版方案：个人版 / 安全版

> 编制：2026-11-05　|　用途：交给 DSH 开发会话执行
> **内部基线，非发布文档。** 对外说明书见 `docs/EDITIONS.md`（已按实现更新：TLS / 证书指纹 / 设备信任已落地）。
> 前置：昨天那份《安全加固清单-对标LocalSend》仍是**条目来源**，本文件解决「哪些条目进哪个版、代码怎么分」。

---

## 一、先定一件事：不建两条 git 分支

用户要的是「个人版 / 安全版」两个产品。实现上有两条路，必须选对：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 两条 git 分支（personal / secure） | 隔离彻底 | 每修一个 bug 要改两遍、测两遍；两周后必然漂移；发布 tag 混乱 | **不采用** |
| B. 一条代码线 + 构建期分版（edition） | 修一次全版本受益；共用代码不重复；两个产物 | 需要严格的分层纪律（安全代码不能泄漏进个人版包） | **采用** |

**git 分支只用于发版标记**（`release/1.5.0-personal`、`release/1.5.0-secure`），不做日常开发分支。

## 二、代码怎么分

```
droplink/
├─ dlcore/                 共用：config / state / fsutil / winenv / media / api / httpd
│  └─ sec/                 仅安全版打包（个人版构建时不进 payload、运行时不 import）
│     ├─ __init__.py
│     ├─ tls.py            自签证书生成/加载、SSLContext
│     ├─ trust.py          指纹计算、信任列表、指纹变更告警
│     ├─ approval.py       传输前确认（prepare / accept / reject / 超时）
│     ├─ tokens.py         逐文件一次性 token
│     └─ pathguard.py      写入侧强约束（realpath/UNC/ADS/软链/保留名）
├─ web/                    共用，按 edition 注入差异
├─ build/build_exe.py      新增 --edition personal|secure
└─ server.py               入口，按 edition 决定 import 哪些模块
```

**三条硬纪律**：
1. `dlcore/sec/` 里的任何文件，**不得被 `dlcore/` 的共用模块直接 import**——只能由入口或 `httpd` 按 edition 动态挂载。个人版包里不允许出现 `sec/` 目录。
2. 安全版多出来的 HTTP 路由，必须在个人版里**不注册**（返回 404，而不是 403），避免暴露能力。
3. 前端的差异只允许通过 `window.__EDITION__` 与 `config.edition` 两个注入点，不许多处判断。

## 三、运行时身份

```python
# dlcore/config.py
EDITION = os.environ.get("DROPLINK_EDITION", "personal")   # personal | secure
def is_secure_edition() -> bool: return EDITION == "secure"
```

- 构建时 `build_exe.py --edition secure` 会把 `EDITION` 烤进产物（同时写入 VERSIONINFO 的 ProductName：`DropLink Personal` / `DropLink Secure`）。
- 保留旧的 `--secure` 启动参数：在个人版里等价于「启用部分加固校验」，在安全版里无效果（已默认全开）。不删除，避免老脚本失效。

## 四、条目归属（对应昨天清单 S-01 ~ S-16）

| 编号 | 条目 | 个人版 | 安全版 | 理由 |
|---|---|---|---|---|
| S-01 | TLS 自签证书 | 不做 | **做** | 安全版的核心卖点 |
| S-02 | 指纹=设备身份 + 信任列表 | 不做 | **做** | 个人版没这个概念 |
| S-03 | 传输前人工确认 | 不做 | **做** | 个人版要的是「拖进去就来」 |
| S-04 | 逐文件一次性 token | 不做 | **做** | 依赖 S-03 的会话 |
| S-05 | 状态码语义统一 | **做** | 做 | 属正确性，不是安全功能 |
| S-06 | 写入侧路径约束 | **做（仅写入侧）** | 做（写入侧 + 更严） | 个人版允许读整机，但**不许写到接收目录外** |
| S-07 | 分接口限流 | 只保留登录退避 | **做** | 个人版限流会干扰正常大文件传输 |
| S-08 | 明文提示 | **做** | 不适用 | 个人版本身就是明文，必须告知 |
| S-09 | 密钥存储 | 不适用 | **做** | 无密钥 |
| S-10 | 日志脱敏 | **做（PIN/token 部分）** | 做（全量） | 两版都不能把 PIN 打进日志 |
| S-11 | 磁盘配额与残留清理 | **做** | 做 | 属稳定性 |
| S-12 | 恶意输入（zip 炸弹/超长名） | **做** | 做 | 属健壮性 |
| S-13 | Host 校验 / DNS rebinding | **做（Host 校验）** | 做（+ Secure Cookie/CSP） | DNS rebinding 对个人版同样是真威胁 |
| S-14 | 安全默认值 | 见第六节 | 见第六节 | 分版定义 |
| S-15 | 发布完整性 | **做** | 做 | 两版都要能验签 |
| S-16 | 威胁模型 / SECURITY.md | **做（写明「不防什么」）** | 做 | 个人版更需要说清边界 |

**一句话**：个人版只吃「正确性 / 健壮性 / 知情权」三类；凡是「让用户多点一次、让传输变慢」的，都归安全版。

## 五、协议差异与兼容

| 项 | 个人版 | 安全版 |
|---|---|---|
| 传输 | `http://IP:8848` | `https://IP:8848`（自签） |
| 握手 | 配对码 → Cookie | 配对码 → 设备指纹登记 → 信任确认 |
| 上传 | 鉴权后直接落盘 | prepare → 人工接受 → token 分片上传 |
| 端口 | 8848 | 8848（TLS），可选 8849 明文仅本机 |

**不兼容是刻意的**：安全版的客户端必须能校验指纹，个人版客户端连不上安全版是预期行为。
必须在两端 README 与 UI 上写清：**「两端必须同一版本族」**，否则用户会当成 bug。

## 六、默认值（分版）

| 开关 | 个人版默认 | 安全版默认 |
|---|---|---|
| TLS | — | 开（不可关） |
| 传输确认 | — | 开（可对「已信任设备」关） |
| 自动接受 | 开（本来就是） | 关 |
| 浏览整机 | 开 | 开，但首次越界弹提示 |
| `--secure` 兼容参数 | 关 | 忽略 |

## 七、构建与发布

```bash
# 个人版（与现在行为一致）
python build/build_exe.py --edition personal -o "dist/DropLink.exe"

# 安全版
python build/build_exe.py --edition secure -o "dist/DropLink-Secure.exe"
```

- 产物名固定：`DropLink.exe` / `DropLink-Secure.exe`
- 版本号共享（1.5.0），VERSIONINFO 的 `ProductName` 区分
- 发布：两个 zip、两个 GitHub Release tag（`v1.5.0-personal` / `v1.5.0-secure`）
- 安卓：同一 APK，首次启动向导选「个人 / 安全」，选择结果存本地并决定连接协议；**不打两个 APK**（维护成本翻倍且用户分不清）

## 八、验收标准（本轮）

1. `--edition personal` 构建产物里**不含** `dlcore/sec/`（解包后 `ls` 验证），行为与 v1.4.7 一致，四套回归全 PASS。
2. `--edition secure` 构建产物能启动，默认 TLS 握手成功，浏览器出现自签证书警告。
3. 安全版访问 `/api/trust`、`/api/approve` 有响应；个人版访问同样路径返回 **404**。
4. 两版 `/api/ping` 都返回 `edition` 字段（`personal` / `secure`），便于排障。
5. 个人版 README 顶部有「明文传输，仅建议在可信网络使用」的提示。
6. 分版说明书（本文档）进仓库 `docs/EDITIONS.md`。

---

## 九、执行顺序（建议两轮）

**第一轮：分版骨架（不加安全功能）**
- 加 `EDITION` 常量、`sec/` 目录（空实现）、`build_exe --edition`、路由按 edition 注册、`/api/ping` 带 edition、两个产物都能跑、四套回归全绿。
- 出口：两个 exe 都能起，个人版行为零变化。

**第二轮：安全版实现**
- 按 S-01 → S-02 → S-03 → S-04 顺序做（每条独立可测）。
- 每完成一条，跑一次个人版回归，确认没把共用代码改坏。

---

## 十、风险提示（给用户看的）

1. **安全版会让「传个文件」变成三步**：确认设备、确认传输、等校验。这是它的价值，也是它的代价。
2. **自签证书必然弹警告**，浏览器端体验会变差；这是局域网自签的固有代价，不是实现问题。
3. **两版不互通**，家里两台设备必须装同一族；如果混装，表现为「连不上」，需要文档提前说明。
4. **安卓单 APK 双模式**会让首启多一步选择；如果嫌烦，可改成构建两个 flavor，但维护成本上升。
